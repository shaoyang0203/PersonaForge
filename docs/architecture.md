# PersonaForge 架构说明

面向想改这套结构、或想把它接进自己系统的人。

## 为什么不是一个超长万能 RP Prompt

一个把所有规则写在一起的长 System Prompt，在长期角色扮演里有四个可预见的失效方式：

1. **低相关规则长期占位。** 推导一段普通日常对话时，用不到伏笔规则、不需要事件三检验，但它们一直占着上下文预算，也占着模型的注意。
2. **规则之间互相稀释。** 文件越长，单条原则被实际执行的比例越低；新增一条往往在削薄已有十条。
3. **无法按场景取舍。** 一段 Prompt 只能整体生效或整体不生效。而"这场景需要哪个能力"这件事是每轮变化的。
4. **表演逻辑与长期状态混在一起。** "怎么推导这个人"和"现在还有什么仍然成立"是两类完全不同的东西：前者稳定、后者高频变化。写在一起的结果通常是——要么状态更新时改动了原则，要么原则改动时破坏了状态记录。

所以 PersonaForge 的分层是：

```text
rp-core.md                    常驻：无法安全按需加载的底层原则
skills/*/SKILL.md             按需：一个能力域的核心推导方法
skills/*/references/          按需中的按需：详细展开、边界、例子（只一层）
skills/*/agents/openai.yaml   OpenAI Skill 格式的 UI metadata
runtime/                      状态：仍然成立什么，与怎么写无关
references/quality-check.md   诊断：出问题时对号，不参与日常执行
examples/                     说明：给读者看通路，不参与执行
```

这些内容分属两层：`rp-core.md`、`runtime/`、`references/`、`examples/`、`docs/` 属于**框架层**，构成完整的 PersonaForge；`skills/` 下的五个目录属于 **Skill 层**，每个都可以独立封装、单独分发。

## 四条设计原则

### 1. 常驻内容尽量少

`rp-core.md` 有一条硬预算：约 600–1200 中文字。它只保留同时满足两个条件的内容——每一轮都有效，且不能安全地按需加载。

判据：**如果一条规则可以在多数轮次里不被触发，它就不该在 core。** 现在 core 里的十条都是这一类：因果链、审美中立、不数值化、信息边界、状态不清零、自主性、意图归属、优先级、最终自检。

任何修订让 core 超过这条预算时，先删再加。

### 2. 方法按需加载

五个 Skill 各自对应一个清晰的能力域，边界写在 `SKILL.md` 的 frontmatter `description` 里。`description` 的任务不是宣传功能，而是**说明什么情况该加载、什么情况不该加载**——每一条都带反向边界：

- character-performance：不要为了让人物显得更复杂而用。
- dialogue-subtext：不要默认所有人物都含蓄。
- relationship-emotion：不要为了展示连续性而强迫情绪残留。
- character-agency：不要为了展示自主性而制造事件。
- story-progression：不要因为场景安静就触发。

这些反向边界存在的理由是本项目的一个基本判断：模型的统计偏好会把所有技巧用成统一审美。触发条件写窄，比技巧本身更容易决定输出质量。

### 3. 表演逻辑与长期状态分离

| | Skill | Runtime Memory |
| --- | --- | --- |
| 回答 | 如何推导 | 现在仍然成立什么 |
| 变化频率 | 几乎不变（方法论） | 每场都变（状态） |
| 内容性质 | 判断程序 | 事实清单 |
| 是否进正文 | 影响正文写法 | 默认不进正文 |

`active-state.md` 是这两层之间的接口：从全量状态里切出当前场景需要参与推理的一小块。它让状态规模不直接压到每一轮的上下文上——Story Memory 可以长期增长，Active State 始终很短。

### 4. 角色卡优先

本项目不重新定义人物。优先级：

```text
角色卡设定
>
用户当场明示
>
故事中已经发生并确认的事实
>
RP Core / Skill 的倾向性描述
```

本项目的条文与上位冲突时让位。"默认""通常""倾向"只在没有规定的地方起推导作用，不是要求，也不是待办清单。

## 框架层与 Skill 层：可移植性规则

一个 Skill 目录被单独复制出去之后，仍然要能被理解和执行。因此本仓库遵守三条：

1. **Skill 不引用自己目录以外的文件。** `SKILL.md` 与它自己的 `references/` 之外没有任何路径依赖。跨能力的分工用名字表述（"这属于 character-agency 的范围"），不用文件路径表述。
2. **不复制整个 RP Core 进 Skill。** 如果某个 Skill 真的需要一个全局前提，只在自己的 `SKILL.md` 里留一两句**自足前提**（现在每个 Skill 开头各有一段：尊重角色卡与已确认事实、不替用户角色做决定、状态不自动失效等）。Skill 独立 ≠ 五份 PersonaForge。
3. **references 只有一层。** 每个重要 reference 都能从 `SKILL.md` 直接找到；不允许 reference A → B → C 的依赖链，也不允许 reference 指向别的 Skill。

框架层与 Skill 层是**叠加**关系：Skill 单独可用；与框架层一起用时可额外获得 RP Core 的底层原则与 Runtime Memory 的跨场景状态（尤其是信息边界与错误理解），那部分状态管理不属于任何单个 Skill。

`agents/openai.yaml` 只是格式适配：提供 `interface.display_name` 与 `interface.short_description`。它不改变方法论内容，也不构成任何运行验证（见 `COMPATIBILITY.md`）。

## 强约束的使用范围

全仓库里"必须 / 禁止 / 永远 / 只能 / 不得"只允许出现在**结构性错误**上：

- 不越过角色的知识边界与主观理解。
- 不替用户角色做决定、不越权改写已确认事实。
- 不把关系与情绪变成数值系统。
- 不把状态每轮清零。
- 不让行动理由落到"这样更有戏"上。

人物风格、恢复速度、关系节奏、表达方式、要不要含蓄——这些一律用倾向表述，并且必须允许人物卡把它们反过来。

## 修订约定

- 本仓库是 PersonaForge 的正式来源。方法论改动直接落在对应文件上：底层原则进 `rp-core.md`，能力域方法进相应 `SKILL.md`，详细展开与边界进该 Skill 的 `references/`。
- 同一条原则只有一个正式出处，其他位置只引用。移动出处时同步改所有引用。
- 新增或修改 Skill 内容时，先确认没有引入目录外的路径依赖（见上面的可移植性规则）。
- `examples/` 里的段落只用于说明结构，不作为可复用模板；新增例子时要在文件内写明这一点。
- 不新增第六个能力域。新的表演问题如果落不进现有五域，通常说明它属于某一域的边界澄清，或者属于题材扩展层。
- 题材扩展（成人向、战斗、RPG 数值、角色卡与世界书模板）作为独立的可选层，不进入 RP Core，也不修改五个 Skill。
